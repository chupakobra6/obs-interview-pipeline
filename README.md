# OBS Interview Pipeline

[![CI](https://github.com/chupakobra6/obs-interview-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/chupakobra6/obs-interview-pipeline/actions/workflows/ci.yml)

После остановки записи OBS или SobesTech проект показывает один и тот же короткий macOS-диалог: обработать запись или оставить как есть, удалять ли рабочую копию после успеха и сводить ли аудиодорожки. Сжатие никогда не начинается без выбора пользователя. Обработанная запись превращается в компактное HEVC-видео и Markdown-расшифровку; оригиналы SobesTech всегда сохраняются.

## Что происходит после остановки записи

1. Lua-hook получает от OBS точный путь последней завершённой записи и неблокирующе открывает `OBS Interview Prompt.app`.
2. Импортёр SobesTech проверяет завершённую пару JSON/MP4, создаёт безопасную staging-копию и открывает тот же prompt ровно один раз.
3. Кнопка «Оставить без обработки» не запускает pipeline; для SobesTech она удаляет только staging-копию. Кнопка «Сжать и расшифровать» кладёт в очередь путь и выбранные для этой записи параметры; macOS `LaunchAgent` запускает один worker.
4. LaunchAgent запускает worker с интерактивным QoS: явная пользовательская обработка не получает системный background throttle. Worker сначала обрабатывает медиаконтейнер, затем вызывает канонический адаптивный `telegram-harvest transcribe-file`; тяжёлые VideoToolbox и Whisper-этапы не конкурируют за ресурсы Mac.
5. Готовый source HEVC `1512x982@30` копируется без повторного video encode; для старого или иного входа включается приоритетный по скорости VideoToolbox transcode и только необходимые `scale`/`fps` filters. Кодирование файла использует `-realtime 0`: при жёстком ограничении битрейта режим реального времени может отбрасывать кадры. Это соответствует [рекомендации Apple для offline compression](https://developer.apple.com/documentation/VideoToolbox/kVTCompressionPropertyKey_RealTime). Битрейт рассчитывается из размера и длительности source, ограничивается через `maxrate` и оставляет запас на muxing: итог не может превышать 80% исходного размера.
6. По умолчанию все source audio tracks сохраняются раздельно и кодируются в AAC с начальным target 96 Кбит/с. Галочка merge сводит их в одну AAC-дорожку с постоянным коэффициентом 1/N: завершение микрофонной дорожки не меняет уровень остальных. Реальные временные смещения сохраняются; пропуски заполняются тишиной. Сначала проверяются streams, codec/bitrate, разрешение, fps, длительность и предел размера. Если stream metadata содержит duration и start_time, сначала проверяется конец каждой сохраняемой аудиодорожки либо самой длинной исходной дорожки при merge с допуском 150 мс. Длительность video/container не заменяет конец звука. Неизвестная stream duration, например в MKV, не подставляется из контейнера. Затем все исходные и итоговые аудиодорожки полностью декодируются и сравниваются по содержимому. Только отказ по энергии или корреляции повышает AAC target до следующего большего значения из 128, 160, 192, 256, 320 Кбит/с. Каждая попытка заново проходит те же проверки; допуски PCM не меняются. ASR начинается после полного успеха.
7. Готовая тройка файлов публикуется одним переименованием каталога. По умолчанию исходник остаётся. При выбранном удалении worker сначала требует успешное сравнение всего звука, публикует результат и повторно сверяет его SHA-256 непосредственно перед удалением. При ошибке исходник остаётся.

Результат записи `2026-08-01 15-49-42.mp4` выглядит так:

```text
~/Movies/Interviews/2026-08-01 15-49-42/
├── recording.mp4
├── transcript.md
└── manifest.json
```

`manifest.json` хранит техническое доказательство обработки: identity и параметры source, точный output probe, ASR timings, флаг подтверждённого Metal runtime и выбранный video mode (`copy` либо `transcode`). Версия 4 также содержит `audio_verification`: охват декодирования, корреляцию, число активных окон и SHA-256 исходника и результата. Перед повторной попыткой удаления worker сверяет source identity, transcript, media probe и текущие байты исходника и результата с этим доказательством. Старый manifest без проверки звука не разрешает удаление.

## Локальный профиль

- OBS canvas: `3024x1964`, физическое Retina-разрешение.
- OBS output: `1512x982`, логическое разрешение macOS.
- Частота: `30 fps`.
- Source: H.265/HEVC через Apple VideoToolbox + три выбранные в OBS AAC-дорожки.
- Final: копия video stream, если source уже HEVC `1512x982@30` и результат укладывается в предел размера; иначе HEVC transcode. По умолчанию те же три дорожки в AAC с начальным target 96 Кбит/с либо одна сведённая дорожка при выборе merge.
- В обоих audio modes каждая аудиодорожка читается через отдельный FFmpeg input/demuxer, а video и metadata – через input 0: всего N+1 inputs, включая запись с одной аудиодорожкой. Это обходит обнаруженный преждевременный EOF AAC при общем demuxer; PCM-проверка всех дорожек остаётся обязательной.
- Video compression: fallback-transcode ограничивает полный результат 80% размера source. Для VideoToolbox вычисляется доступный video bitrate после бюджета AAC; двухпроцентный запас покрывает muxing variance.
- ASR: единый production-вход Telegram Harvest сам выбирает short либо protected long-form по длительности и leading silence. Short-form сохраняет быстрый `no_timestamps` decode, но определяет язык автоматически. Для интервью bounded Silero находит первую и последнюю речь, сохраняет секундный lead-in, физический 15-секундный probe выбирает language policy, после чего timestamped request ведёт контекст до конца. Если корректный ответ пропустил последнюю речь, Harvest один раз перераспознаёт интервал до 45 секунд и заменяет только конечные сегменты, начиная с границы сегмента с контекстом до 20 секунд, сохраняя предыдущий текст. Повтор и итог обязаны пройти прежние проверки покрытия с допуском 2 секунды. Harvest проверяет duration/timestamps, хвост и extreme repetition и возвращает contract v4: `profile_id=adaptive-media-v2`; допустимые результаты — `transcribed`, `coverage-validated` и `no-speech`. В последнем случае расшифровка содержит «Речь не обнаружена». OBS не передаёт ASR-настройки и не содержит отдельного профиля.
- Уведомление: клик по success notification открывает Finder сразу в каталоге готового собеседования.

## Установка и проверка

Требуются macOS, OBS Studio, Go 1.27.2 для сборки, соседний [Telegram Harvest](https://github.com/chupakobra6/telegram-harvest) в `/Users/igor/projects/telegram-harvest` с готовым ASR runtime и `ffmpeg`. `go.mod` закрепляет toolchain; стандартный `GOTOOLCHAIN=auto` загружает его при необходимости:

```bash
brew install ffmpeg
```

```bash
make setup
make check
make test-audio
make install
make doctor
```

`make install` устанавливает:

- бинарник и конфигурацию в `~/Library/Application Support/obs-interview-pipeline`;
- Lua-hook в `~/Library/Application Support/obs-studio/scripts`;
- `com.igor.obs-interview-processor.plist` в `~/Library/LaunchAgents`;
- `com.igor.sobestech-importer.plist` в `~/Library/LaunchAgents`;
- собственный `OBS Interview Notifier.app` в каталоге pipeline — внешняя notification-утилита не нужна;
- собственный `OBS Interview Prompt.app` с выбором параметров конкретной записи.

Повторный `make install` мигрирует старую конфигурацию до текущей схемы и сохраняет пользовательские output/delete defaults.

В настройках фоновой работы macOS службы имеют разные понятные имена: `OBS обработка записей` и `SobesTech импорт записей`. Установщик создаёт соответствующие исполняемые файлы в `bin/` каталога pipeline, направляет LaunchAgents, Lua-hook и prompt на новые пути и удаляет заменённый установленный `bin/obs-interview-processor`. Путь обработчика в Lua-hook задаёт установщик; прежнее сохранённое поле `processor_path` больше не используется. Локальный CLI репозитория остаётся `bin/obs-interview-processor`; это инструмент ручного запуска. Повторная установка сохраняет новые имена служб.

Lua-hook один раз добавляется через `OBS → Сервис → Скрипты`. OBS сохраняет путь в текущей коллекции сцен и загружает скрипт при следующих запусках.

## Где смотреть состояние

```text
~/Library/Application Support/obs-interview-pipeline/
├── config.json
├── queue/
├── done/
├── failed/
├── sobestech-imports/
└── logs/
```

- `queue/` содержит ожидающие записи; наличие файла автоматически будит worker.
- `done/` и `failed/` сохраняют компактный статус каждого задания.
- `logs/processor.log` и `logs/processor-error.log` показывают фоновые запуски.
- `sobestech-imports/` хранит устойчивые receipts импорта и исключает повторную постановку одной записи в очередь.
- success notification открывает `~/Movies/Interviews/<recording>/`; error notification — каталог исходной записи. Для `OBS Interview Notifier` используется стиль «Временно»: баннер исчезает с экрана, но остаётся в Центре уведомлений. Невидимый helper живёт, пока карточка доступна: клик открывает нужную папку, а ручная очистка карточки завершает helper без фонового хвоста.

Проверка окружения:

```bash
bin/obs-interview-processor doctor
```

Ручная постановка конкретной новой записи в очередь:

```bash
bin/obs-interview-processor enqueue --delete-source=false --audio-mode=preserve "/Users/igor/Movies/recording.mp4"
```

Ручная проверка импорта завершённых записей SobesTech:

```bash
bin/obs-interview-processor import-sobestech
```

## Автоимпорт SobesTech

`com.igor.sobestech-importer` следит за каталогом `~/Library/Application Support/com.pers0na2.identityproxy/interview_recordings` и дополнительно проверяет его каждые 30 секунд. Импортёр принимает только пару JSON/MP4 со статусом `completed`, без ошибки и с совпадающим размером; после последнего изменения обоих файлов ждёт 15 секунд, проверяет медиапотоки и показывает тот же диалог, что после остановки OBS.

MP4 атомарно копируется в `~/Movies` под именем времени записи. При отказе от обработки удаляется только эта staging-копия; при согласии она ставится в очередь с выбранными параметрами. Исходный MP4 SobesTech не изменяется. Квитанция сохраняет факт открытия диалога после перезапуска, а поиск задания в `queue/done/failed` обновляет статус после выбора. Неизменившаяся запись с сохранённым решением проходит повторный обход без медиапроверки; квитанция перезаписывается только при изменении задания или его статуса. Обновление технических настроек сохраняет решение пользователя и параметры уже созданного задания. При изменении исходника выполняется нужная проверка; уже опубликованный результат без задания дополнительно связан с состоянием выходных файлов, поэтому их изменение требует проверки результата.

Для ошибки сохраняются причина, зависимости и условие возврата. Первые повторы назначаются через 30 и 60 секунд. После трёх отказов неисправный вход ждёт изменения JSON, MP4, связанных файлов или инструмента; восстановление зависимости снимает ожидание. Временная недоступность `ffprobe` или сбой открытия диалога после этих попыток проверяются не чаще одного раза в 15 минут. Успешный возврат очищает состояние ошибки; остальные записи продолжают обрабатываться независимо. Ошибка показывается уведомлением и остаётся в `logs/sobestech-importer-error.log`.

## Инварианты безопасности

- Worker не сканирует старые файлы в `~/Movies`; он обрабатывает только пути, переданные OBS hook или проверенным импортёром SobesTech.
- Вход обязан быть обычным непустым `.mp4`, `.mov` или `.mkv` внутри `allowed_input_dir`.
- Jobs выполняются последовательно: два ASR/VideoToolbox pipeline одновременно не запускаются.
- Проверенный сжатый файл сохраняется в скрытом checkpoint-каталоге при последующей ошибке ASR. Retry сверяет source identity, параметры обработки и полный media probe, затем повторяет только ASR; повреждённый или устаревший checkpoint автоматически пересобирается.
- Сжатие и ASR имеют отдельные safety timeouts, зависящие от длительности записи. Общий бюджет сжатия – половина длительности записи, минимум две минуты: он учитывает offline HEVC и полную проверку звука. Все попытки сжатия, probe и PCM-проверки делят один deadline: максимум шесть AAC targets и два video modes на target. Ошибки декодирования, SHA-256, source identity и отмена завершают этап без повышения bitrate. Исходник и валидный checkpoint остаются для диагностики и безопасного retry.
- Во время encode рядом с временным видео существует машинный `.progress`-файл ffmpeg с обработанным медиавременем и фактической скоростью. После завершения или остановки этапа он удаляется.
- При ошибке ASR, компрессии, проверки или публикации исходник остаётся на месте; `unlink` начинается только после этих gates. Если worker завершился уже после успешного `unlink`, retry распознаёт это состояние по валидному опубликованному результату.
- Device/inode, размер и modification time source фиксируются до работы и повторно проверяются перед публикацией и `unlink`; файл, заменённый по тому же пути во время обработки или retry, не удаляется.
- Retry после публикации требует точного совпадения transcript и media probe с manifest. Если предыдущий worker уже удалил source, повтор считается успешным только для `delete_source=true` и только после повторной проверки опубликованного результата.
- Если копия HEVC превышает 80% размера source, worker один раз повторяет тот же AAC target с явным HEVC transcode и video budget после вычета фактического выбранного AAC target. Если transcode также превышает предел, исходник сохраняется. Для тишины средний bitrate может быть заметно ниже target. Manifest хранит выбранный target и краткий список предыдущих неуспешных попыток.
- Повтор после сбоя удаления заново проверяет уже опубликованные результаты и только затем повторяет удаление source.

## Проверка сохранности звука

`make test-audio` запускает адресные проверки сравнения PCM, сведение и сохранение отдельных дорожек, потерю хвоста при полной длительности AAC, подмену звука, тишину и запрет удаления по старому manifest. Используются только синтетические записи из временных каталогов. Отдельный `make test-audio-long` создаёт 33-минутную запись с микрофонной дорожкой до 32:30 и проверяет весь результат. Этот прогон отделён от обычного `make check`.

Проверка читает все mono/stereo дорожки до конца, приводит их к общей временной шкале и сравнивает каждый стереоканал в окнах по 200 мс на 48 кГц. Для preserve сравнивается каждая пара дорожек; для merge эталон суммируется в Go независимо от фильтра `amix`. Контролируются энергия и корреляция с допуском на AAC и задержку до 20 мс. Противофазное уничтожение активного звука, пропажа хвоста, ошибка декодирования, timeout или неподдерживаемые каналы дают отказ с сохранением исходника. Законная тишина не считается ошибкой. Это техническая проверка сохранности слышимого содержимого, без оценки точности расшифровки и без обещания побитового совпадения AAC.

Проверенный compression checkpoint версии 2 связывает эту проверку с исходником и SHA-256 сжатого файла. Повтор после ошибки ASR использует его только при сохранности этих зависимостей. Checkpoint и опубликованный результат принимают выбранный AAC target только из текущей допустимой последовательности; media validation использует этот target. Проверка PCM версии 2 дополнительно сверяет число декодированных кадров с известным концом каждой исходной и итоговой аудиодорожки. Два одинаково оборванных декодера не могут подтвердить полное покрытие. Доказательство версии 1 пересобирается; опубликованный результат с ним отклоняется без удаления исходника. Retry также проверяет SHA-256, в том числе после уже выполненного удаления. Probe включает stream duration/start_time; несовпадение с текущим probe также требует пересборки checkpoint. Метаданные и наличие текстовой расшифровки сами по себе не разрешают удаление.

Изменение 22.10.2026 закрывает потерю исходника при неполном аудиорезультате. В записи эфира 21.10 оба итоговых канала содержат тишину после 32:30,5. Время совпадает с отключением микрофона, но 18 синтетических вариантов со старым `amix` не воспроизвели сбой. Точная причина преобразования старого файла не подтверждена; исходник к моменту расследования уже отсутствовал.

В записи эфира 22.10 воспроизведён преждевременный EOF при чтении нескольких аудиодорожек через общий FFmpeg input: video длиной 3:16:04,8 сопровождалось звуком только до 5:31,817. Независимые inputs сохранили весь звук и прошли полное PCM-сравнение. Отдельно AAC 96/128 Кбит/с менял тихий широкополосный сигнал сверх допуска; повышение до 160 Кбит/с прошло ту же проверку. Оба исправления сохраняют исходник при любом отказе.

## Границы ASR

`coverage-validated` подтверждает структуру timestamps и покрытие хвоста, но не точность каждого слова или WER/CER. Определяется доминирующий язык; переключение языков внутри одной long-form записи остаётся отложенным. Short-form использует `language=auto` без отдельного probe, prompt или timestamps.

Модель, Metal и быстрые decode settings принадлежат Harvest. При сравнении long-form алгоритмов медианное время не должно ухудшаться более чем на 10% без доказанного выигрыша качества и отдельного обоснования. Проверять RU/EN, слабую речь, leading silence, no-speech, начало/середину/конец, повторы и prompt leakage; реальная запись с silver reference не заменяет ground truth.

[Проверка унификации ASR](docs/benchmarks/unified-adaptive-asr-benchmark.md) сохраняет доказательства выбора одного публичного профиля. Локальный ASR-вход не выполняет Telegram RPC и не меняет Telegram state.

[Замеры прежних версий](docs/benchmarks/unified-adaptive-asr-benchmark.md#historic-measurements) сохранены отдельно. Они показывают условия и результат тех запусков; скорость текущего полного задания оценивается вместе со сжатием, распознаванием и публикацией.
